Images, and what lisptc already is

What an image is from scratch, what ASDF adds on top, how much of both lisptc has today, and a staged plan for the rest.

1 · In plain terms

The usual mental model

You write source files. You build. You get a process. The process runs, then dies. Your program is the files on disk, and the process is a disposable thing you spin up from them. Change a line and you kill the process and start another. Every time.

Lisp's model

The live process is the program. Files are a convenient way to get things into it. That live process is called an image.

The name is literal. In Common Lisp you can dump the whole running process to disk, memory and all, and boot it tomorrow in exactly the state you left it. SBCL's function for this is named save-lisp-and-die. It is an image the way a disk image is: a snapshot of everything.

What is inside one

Every function you have defined. Every variable and its current value. Every class, macro and error type. A REPL waiting for input. And the compiler itself.

That last one carries the weight. The compiler stays inside the running program, so the program can compile new code into itself while it runs. Most languages leave the compiler outside at build time, and the running process has no way to grow.

How you work with it

You do not run a file and wait for output. You start an image and it stays up for hours or days, with your editor connected to it. You write a function, hit a key, and that one definition goes into the live image. Nothing restarted. Nothing rebuilt. The variable you spent ten minutes setting up three hours ago is still sitting there holding its value.

It is a workshop you stand inside of, rather than a thing you assemble and launch.

Why redefining works at all

Here is the whole mechanism, and it is simpler than it sounds. A caller does not hold a copy of the function it calls. It holds the name, and looks up what that name points to at the moment of the call.

Think of a labelled box on a shelf. serve knows "find the box labelled greet, use what is in it". It does not know or care what is in the box. Redefine greet and you have swapped the contents. Every caller in the image gets the new thing instantly, and none of them were touched.

In most languages the caller grabs the actual function when the module is first imported and keeps it. Swapping the original later changes nothing, because everyone already holds their own reference. That is the real reason you restart.

The catch nobody mentions first

Images drift. After six hours your image holds functions you defined at the REPL and never wrote to a file, a variable you set by hand, and an old version of something you renamed that is still sitting in its box because nothing removed it. The image no longer matches your source, it works, and it will not work for anyone else. "Does it still run from a cold image?" is a question Lisp programmers learn to ask on purpose.

2 · What ASDF adds

One definition at a time is fine while you type. A real system is fifty files.

ASDF knows which files make up a system and what order they load in. (asdf:load-system :my-app) re-reads the files that changed and evaluates their top-level forms into the live image. Each defun swaps a box. Each defclass redefines a class, and CLOS walks existing instances to the new shape through update-instance-for-redefined-class. define-condition redefines an error type.

It is the nearest thing Lisp has to a build step, except it produces no artifact. It pours changes into something already running.

So the original paragraph has two halves, and they are different sizes of work:

  • The Lisp half — globals in one mutable table, callers late-bound to it. This is a property of the evaluator.
  • The ASDF half — a named system, a load order, change detection, reload. This is tooling built on top.

The headline

lisptc already has the Lisp half, and nothing in the repo says so. An agent that defines (defun triage-issue ...) on turn 4, watches it fail on turn 9, and redefines it on turn 10 gets the new body everywhere, immediately, with no reset. That works today.

What is missing is the ASDF half. And section 4 is the reason that half is not optional.

4 · The macro boundary

This was the one open question on the previous version of this page. It is answered, and the answer reshapes the plan.

A lambda body is compiled eagerly, at definition time. Compilation expands every macro in the body and stores the expanded form in the closure (compile.ts:42, reached from lisp.ts:276). The closure then runs that fixed body on every call.

(defmacro twice (x) `(progn ,x ,x))
(defun go () (twice (step)))     ; compiled now; twice is already expanded away

(defmacro twice (x) `(progn ,x ,x ,x))   ; redefine the macro
(go)                             ; still two steps. go holds the old expansion.

(import "that-file.ptc")         ; re-evaluates the defun, recompiles, re-expands
(go)                             ; now three.

So the image has two tiers, and the distinction is the single most practical thing on this page:

Live immediately

Redefining a function. Every caller reaches it through the shelf slot at call time, so one defun patches the whole image.

Needs the callers reloaded

Redefining a macro. Callers compiled it away already. Only re-evaluating their definitions picks it up.

This is not a lisptc defect. Common Lisp behaves the same way, and "redefining a macro means recompiling its callers" is standard knowledge there. It is also the clearest answer to why ASDF exists at all: if one-definition-at-a-time covered everything, nobody would need a system that reloads files in order.

Which means a reload is not a convenience layered on an image that already works. It is the half that makes macro-level change possible at all, and the lisptc prelude is largely macros.

5 · Three uses, and they are not one feature

A · operator patches a live agent

Fix a prelude bug or an extension's .ptc prompt without dropping in-flight threads out of ReplStore. The paragraph's literal claim, and the weakest fit here: most of what you would want to patch lives in TypeScript, where none of this applies.

B · the agent patches itself

It wrote triage-issue, the call failed, the diagnostics extension told it why, it redefines the function, the next call takes the new body. Already true today for functions. The work is naming it and teaching it in a prompt.

C · durable skills

The agent writes a definition to a file through a port, the image reloads it, and the skills come back across process restarts by reloading the system. Where ASDF's system concept earns its place, and the one with real product value.

Worth stating plainly, because it shapes phase 4: the memory extension holds facts the agent recalls. An image holds procedures the agent runs. Complements, not competitors, and lisptc persists only the first today.

6 · The plan

Three repo constraints decide the shape. A new language surface goes in an extension, never the interpreter. Everything reaching the filesystem goes through a port the extension declares. Nothing above an extension names it, so neither the REPL nor the agent loop can call a reload directly.

Phase 0 — pin what already holds

Nothing new ships. Tests in packages/interpreter/test that fail if any HAVE row is ever broken:

  • redefining a global patches a caller compiled before the redefinition
  • importing the same file twice re-evaluates it
  • undefineGlobal makes a name unresolvable again
  • and the negative: a redefined macro does not reach an existing caller until that caller is re-evaluated

Today nothing fails if someone adds a module cache to importFile as an optimisation and silently kills reload. The repo's own rule is that a constraint worth keeping is a test that fails when it breaks. That last bullet matters most: it pins a surprising behaviour as deliberate rather than leaving the next reader to discover it.

Phase 1 — packages/image, one new extension

@repo/image-extension, shaped like packages/diagnostics: src/image.ts, src/ports.ts, src/image-host.ts, src/image.ptc.

Surface (image/load "path"), (image/reload), (image/loaded), (image/forget 'name).

Port read(path), mtime(path), watch(paths, cb). The extension imports no node:fs, and check:arch will say so if it tries.

The model to copy is already in the repo. The MCP extension defines a group of bindings on load and withdraws them on unload with undefineGlobal. An image file is the same shape: a source, the names it owns, and a withdrawal. Read mcp.ts:276 before designing anything.

Provenance is the one open design choice. There is no hook on global writes, so:

Stale removal on reload of F, names attributed to F before and absent after get undefineGlobal. This is what a bare re-import cannot do, and the reason the extension exists rather than a one-line alias.

Phase 2 — asking for a reload from outside

No protocol change. session-server already has an eval op, and (image/reload) is a form. A dedicated reload op would only matter in a REPL built without the extension, and the layering rules say you should not want that.

apps/cli gets :reload beside :clear and :up, plus a --watch flag that re-sends it on mtime change. The CLI is a composition root, so it may hold the watcher itself.

Phase 3 — reloading under a running agent

A reload must never land mid-evaluation. The extension hooks the beginTurn chain and applies pending reloads between steps.

Again the worked example exists: MCP loading "runs off an async broker and applies between evaluations". Same problem, same answer. Do not invent a second mechanism.

The reload should leave an annotation on the step, so an eval trace shows the image changed under the turn. Otherwise replaying that run is quietly not reproducible, which cuts against the deterministic-brain thesis.

Phase 4 — the system, and persistence

ASDF's actual contribution, and the payoff for use C.

  • A system.ptc per workspace: the files, in load order. Order matters more than it looks, because of section 4: a file defining macros must load before the files whose bodies expand them.
  • @repo/backend supplies a store satisfying the image port, so a workspace's skills live in Convex rather than on a container's disk.
  • openWorkspaceRepl loads the system when it opens a REPL, so learned procedures survive a deploy.
  • Name it twice. An extension on the served agent is composed in @repo/backend/src/agent-repl.ts and named in apps/api, or it ships without its prompt. apps/api/test/runtime-assets.test.ts is what catches the omission.

Only here does the comparison to ASDF hold end to end: a named system, a load order, change detection, reload into a live image.

Phase 5 — what not to build

  • No eval of strings in the core dialect. There is deliberately none. Adding one costs the static arity checking the LSP does and weakens what diagnostics and compaction can say. An agent defining something writes a form, not a string.
  • No condition system or restarts. The CL story is "redefine the broken function and resume the frame". lisptc has try/catch and no frame resumption, so the honest version is redefine and retry the turn, which the agent loop already gives you. A large dialect change chasing a small gain.
  • No CLOS-style instance migration. There are no instances.

7 · What this costs you

RiskWhyWhat to do
Macro changes need their callers reloaded Bodies are compiled eagerly and macros expanded away at compile.ts:42. Confirmed, and it matches Common Lisp. Reload by file, never by single definition. It is the reason phase 1 exists. Pin it with a test in phase 0.
A closure already handed out keeps the old body Late binding patches calls that go through the name. A function value stored in an alist, captured by a promise handler, or passed to a port is the old object and stays the old object. Accept it. Reload between steps; in-flight promises finish on the old body. Do not chase references.
Image drift The oldest problem in Lisp, inherited whole. After a long session the image holds definitions no file accounts for. Make the system file the source of truth and make a cold reload routine. (image/loaded) should show what came from where.
A reload makes a turn non-reproducible The run's result now depends on when a file changed, and no trace records that. Annotate the step. Phase 3.
Stale removal by diff misattributes Two files defining one name: the diff credits whichever loaded last, and reloading the other may delete a live definition. Refuse to remove a name claimed by two files, and say so. Or take the defined chain.
Self-patching widens what the agent does to itself Use B plus phase 4 means a model's output changes what later turns execute, durably, across sessions. A deliberate decision, not a detail. Writes stay behind the port, the system file stays reviewable.

Still open

Per-workspace or per-thread? Extensions are composed per workspace in agent-repl.ts, but ReplStore keys REPLs per thread. A workspace's learned skills probably want to be shared across its threads, and that is not the shape the store has today. This is the only question left that blocks design rather than implementation.

Smallest honest first step: phase 0, plus the prompt half of use B. No new package, and it names and protects a property the repo already has and documents nowhere.
