Onboarding Relevance Funnel

How the agent should suggest a saved onboarding only when it fits what the user is doing. Each stage is cheaper than the next and can stop early, so most messages never reach a model, and the rest make at most one shared call.

Already built

@repo/onboarding-extension gives the agent (onboardings), onboarding/read, create, update, run, done and done?. A script is a quoted lisptc form, usually a ui/tour, run the way memory/replay runs.

Convex keeps onboardings per workspace as printed source and onboardingProgress per user (started / done). The sidebar has an onboarding/ folder with a read-only source page. The first-message note was dropped.

Per user message

The funnel

1

Eligibility

free · local

An onboarding is a candidate only when the user's status is new, it isn't cooling down after a decline, it wasn't already offered in this chat, no tour is on screen, and the message is the user's own (not an event or sub-agent notice).

The extension caches the candidate list in the REPL, the way ConvexMemoryStore caches memories, and updates it on its own writes.

no candidates → stop. A user who finished everything costs nothing again.
2

Triggers the author declares

free · certain

Each onboarding says when it applies, in the trigger language memories already use. A hit means relevant, no model.

(onboarding/create "upload-files" '(ui/tour ...)
  :about "how to give me files"
  :on (any-of (user "upload|pdf|attach") (error "no such file")))

call triggers catch the agent reaching for a form the onboarding covers; error triggers catch a stuck user. The matcher (evalPattern, structurally) moves from packages/memory into @repo/interpreter so both extensions share it.

3

Lexical prefilter

free · local

With no trigger hit, rank candidates against the message with the search engine memory uses (@repo/shared/search), over each onboarding's about line and its tour steps' :say text.

below the score floor → stop.
4

One shared judge call

≤ 1 model call

Extensions never call a model. They propose labels such as {owner: "onboarding", id: "upload-files", about}. The runtime in packages/ai merges every extension's labels plus a none label into one classify call, then hands each result back to its owner.

Accept a label only when its probability clears a threshold and beats none by a margin. The judge (a Jev client, or the structured-output fallback) is passed in once by the composition root.

5

Remember the answer

one write

Nothing is suggested twice. Progress gains offered (with a timestamp) and declined, each with a cooldown. An optional :covers pattern marks it done when the user's own forms run what it teaches.

Progress per user

Statuses

new→ offered→ started→ done · declined

Dashed statuses are new. A skipped tour or a "no thanks" becomes declined, with a longer cooldown than offered.

What the agent sees

Delivery

One private line at the next step, the way fired memories arrive. The main agent, already running, decides whether and how to offer it. The background part only gates: it never starts a turn and never speaks to the user.

<onboarding> "upload-files" fits what the user asked (trigger).
offer it: (onboarding/run "upload-files") </onboarding>

Build order

Three steps

Stages 1, 2 and 5

No model and no new hook point: triggers run at step start, as memory triggers already do. Covers most of the value.

Stage 3

Add the lexical prefilter once real triggers prove too blunt.

Stage 4 and heard

Build the shared judge when a second background consumer, the memory curator, exists. Only then does one merged call pay for itself.

Guardrails
  • A per-workspace budget for judge calls.
  • Skip the model whenever there is nothing to classify.
  • Record each judge call in the turn trace.
  • An eval case per background job in apps/trace-viewer/evals.
