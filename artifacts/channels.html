What the channels
carry

One evaluator speaks to two audiences at once: the person watching the terminal, and the model whose context it is steering. Channels is the bus that splits them — and the place where the split has quietly stopped being the thing doing the work.

How it works today

The one that confuses everyone: write()

			

				
write is not the transport. It is a module-level global in
					lisp.ts whose default is a no-op, and every Interp subscribes it
					to its own USER channel in the constructor.

			

			
// lisp.ts:29 — one global, shared by every Interp in the process
let write: (s: string) => void = () => {};

export function setWriter(fn) { const prev = write; write = fn; return prev; }

// lisp.ts:569 — in the constructor of every interpreter
this.channels.on(USER, (d) => write(d.text));

			

				
Only cli.ts ever installs a real one (process.stdout.write); the
					tests swap it to capture output and restore it afterwards. Nothing in
					apps/api calls setWriter, so on the server every
					USER record reaches a function that does nothing and is discarded.

				
Output reaches the browser by an entirely separate route: the REPL accumulates the
					channels into two strings and returns them as a value. write() is a
					vestigial second exit that only the terminal uses — which is why adding a channel
					the frontend can listen to is not a matter of pointing write somewhere new.

			

		

	






	

		

			The problem
			
Severity is doing a channel’s job

			
Three separate consumers subscribe to MODEL. Each one immediately partitions the
				stream by severity, and no two partitions agree. That is the tell: the bus is
				carrying two unrelated streams down one wire and asking every reader to sort the mail.

		

		

	






	

		

			A better shape
			
Typed topics, explicit audience, a recorded step

			
Three changes, independent of each other. None of them closes the bus to new extensions
				— that constraint is what rules out the obvious fix of one big discriminated union.

		

		

	






	

		

			The new requirement
			
A channel the frontend listens to

			
Generative UI: the interpreter emits a component, the browser renders it. JSON describing a
				component at first, a serialised component later. This is the requirement that turns the
				refactor from tidying into work that has to happen — because today there is no way to
				get a structured payload out of the interpreter at all.

		


		
Where the structure is lost

		


		

			
The two-audience split already survives all the way to the wire: content is what
				the model reads, additional_kwargs.display is what the person reads. It
				survives as two flat strings. A component spec would have to be smuggled inside the
				display string and re-parsed in the browser, and every channel record that is not
				USER or MODEL text is dropped before it reaches the stream at all.

Routing is to, not topic. The rule you want — render what
				is for the person, hide what is for the model behind a debug toggle — is a filter on
				one field, which is only possible once audience stops being encoded in the channel name.

		


		
What a transport costs that an in-process bus did not

		

			

				ordering across a reconnect
				
An in-process listener cannot miss a record. An SSE client can drop and resume, so every
					envelope needs a seq and the stream needs to honour
					Last-Event-ID — or the browser silently renders a hole.

			

			

				backpressure and closure
				
emit returns void today. stream.ts already tracks a
					closed controller and breaks its loop on a failed write; a transport that cannot report
					failure throws that away. Hence send(): boolean.

			

			

				a second serialisation boundary
				
Payloads stop being any JS value and become whatever survives JSON.stringify.
					That is a real constraint on value?: unknown today — a Lisp
					Cell in an error's value does not cross the wire intact.

			

			

				the step boundary becomes load-bearing
				
Batching per step is what the REPL's accumulate-then-return does for free. Streaming
					envelope-by-envelope means the browser sees a partial step, so step has to
					ride on the envelope and the UI has to tolerate a step still in flight.

			

		

	






	

		

			Honestly
			
What each shape is good at

			
The bus is not a bad design. It is a deliberately loose one, and looseness bought real
				things — some of which the replacement gives back.

			If it were mine to sequence
			
      What I would actually do
      
		
      
		
      
			
      The generative-UI channel changes this answer. Read on its own, the bus has
				one defect that costs correctness and several that cost clarity, and I would have said the
				audience work buys tidiness rather than correctness — not worth touching every emit
				site for. A channel the frontend listens to makes that wrong: you cannot route on audience
				from the browser while audience is spelled as a channel name, and you cannot stream a
				component through a pair of accumulated strings. Audience and payload typing become
				load-bearing, so they move to the front.
      
			
      What does not change: the bus stays open. A discriminated union over every record would close
				the set an extension can contribute to, which fights the plugin model the rest of the
				interpreter is built on. Typed topics give the compiler the same grip without that.
      
			
      The Step recorder is the one I would push back on hardest if someone proposed it
				to me. It makes the current implicit behaviour explicit, which is good, but it does not fix
				attribution for work that settles after the step ends — a promise from
				(load-mcp …) resolving into whichever accumulator happens to be live.
				Fixing that properly wants AsyncLocalStorage, which is a
				node: import in the core — and the host-ports work just spent a refactor
				getting those out. It would have to arrive as a port, and at that point the cure is bigger
				than the disease.
      
			
      
				
      firstEnvelope: topic + toPull audience out of the channel name. Everything else depends on it, and it is what lets the browser filter without parsing.
      
				
      firstSplit the MODEL lanesNotes get their own topic. Falls out of the envelope work, deletes the severity partition from all three consumers, and stops critical vanishing.
      
				
      thenChannelTransportOne port, three implementations. Retires the write() global and the REPL's hand-rolled accumulation in the same move.
      
				
      thenThe ui topicOnly meaningful once an envelope can carry a typed payload to a named audience over a real transport.
      
				
      lastStop swallowingIndependent of all of it and a one-line change: report listener failures instead of discarding them.
