Yield, Not Await

A tree-walking evaluator that can call a remote tool mid-form, without a single async in the evaluation path. The entire mechanism is 44 lines and two functions, and it is the reason one interpreter can serve both a language server that must never block and an agent that waits on the network.

01

The problem is colour, not waiting

Waiting is easy. The hard part is that in JavaScript, waiting is contagious. Put one await inside the evaluator and the keyword climbs the whole call graph: every caller of evalGen becomes async, every caller of those becomes async, and the type of "evaluate this form" changes everywhere at once.

For this interpreter that would not be an inconvenience, it would remove a feature. The language server builds its own interpreter and loads the prelude with runSync, then reads doc records straight out of it to answer completion and hover — a path that must return a value, not a promise. The agent, on the very same evaluator, has to call an MCP tool in the middle of an expression and wait for the network.

the counterfactual

One evaluator that is async forces the LSP to either block or fork a second, synchronous evaluator. Two evaluators means two sets of semantics, and they drift.

So the requirement is precise: a form must be able to wait without the act of waiting appearing in any signature between it and the top. That is not a concurrency problem, it is a plumbing problem, and generators are the plumbing.

02

One type carries the whole idea

Evaluation does not return a value. It returns a generator that will eventually produce one, and that may hand out promises along the way.

packages/interpreter/src/drive.ts:5 
export type Eval<T = unknown> = Generator<Promise<unknown>, T, unknown>;
//                                        ↑ what it yields  ↑ what it returns
//                                        a thing to wait   the actual value
//                                        for               of the form

Read the three parameters as a contract. Yields a promise: "I cannot continue until this settles." Returns T: the real result of the form. Receives unknown: whatever the driver sends back in when it resumes.

Nothing in that type says how waiting happens, or whether it is allowed at all. That decision is deferred to whoever consumes the generator — which is the entire trick.

03

Six lines bridge a port to the protocol

Extensions reach the world through ports they declare, and a port that may have to wait is typed Awaitable<T> — T | Promise<T>. A file-backed memory store answers immediately; a Convex-backed one answers with a promise. The call site is identical for both, because of this:

packages/interpreter/src/drive.ts:7 
export function* settled<T>(value: Awaitable<T>): Eval<T> {
  return value instanceof Promise ? ((yield value) as T) : value;
}

A plain value passes straight through and the generator never yields — no suspension, no cost, not even a microtask. A promise becomes a yield, and the value the driver sends back is returned as if it had been there all along.

At the call site the difference is invisible:

packages/memory/src/memory.ts:571 — inside a defGen builtin 
const memory = yield* settled(bank.store.get(key));
// local file store  → returns immediately, no suspension
// Convex store      → suspends here, resumes with the Memory
// the code above does not change, and cannot tell which happened
why this matters for the layering

An extension declares a port and is handed an implementation by a composition root. Because the port is Awaitable and consumed through settled, the root may hand it a local store or a remote one without the extension changing shape. Suspension is what makes host ports substitutable across the sync/async boundary.

05

yield* is the whole propagation story

Every descent in the evaluator is a delegation, not a call:

packages/interpreter/src/lisp.ts — inside evalGen 
frame[i] = a instanceof Cell ? yield* this.evalGen(a, env) : this.evalNow(a, env);
x        = yield* this.evalProgN(body, env);
x        = yield* this.evalCond(arg, env);
[nx,env] = yield* this.evalTry(arg, env);
result   = yield* hooks.evalForm.run(…)   // even the extension seam

yield* forwards every yield outward and every sent value inward, through any depth, for free. That is why adding a suspending builtin required no change to evalCond, evalProgN or evalTry: they were already delegating.

The last line is the one worth pausing on. runGen delegates into the extension chain, and SessionHooks.beginTurn is typed Chain<[ctx], Eval<void>>. An extension's lifecycle hook can suspend by exactly the same route as a builtin — the memory extension waits on its store during beginTurn and nothing above it becomes asynchronous.

06

Two drivers, and a refusal that is a real error

Consuming a generator is where policy lives. There are exactly two policies, twenty-six lines apart in the same file.

packages/interpreter/src/drive.ts:15 — refuse to wait 
export function driveSync<T>(gen: Eval<T>): T {
  let step = gen.next();
  while (!step.done)
    step = gen.throw(new EvalException(
      "cannot suspend", "this host evaluates synchronously", false));
  return step.value;
}

The detail that makes this good: it does not return an error code or hang. It throws into the generator, at the suspension point. So "cannot suspend" arrives as an ordinary EvalException, carrying the form it happened in, catchable by a Lisp (try …). A synchronous host does not get a degraded language — it gets a language where waiting is an error you can handle.

packages/interpreter/src/drive.ts:32 — agree to wait 
export async function driveAsync<T>(gen: Eval<T>): Promise<Outcome<T>> {
  let step = gen.next();
  while (!step.done) {
    let resumed: unknown;
    try { resumed = await step.value; }
    catch (ex) { step = gen.throw(ex); continue; }   // rejection → Lisp condition
    step = gen.next(resumed);                       // value → back into the yield
  }
  return { value: step.value };
}

Eight lines of loop. await appears exactly once in the entire evaluation path, here, at the top, where it colours nothing beneath it.

the error path is the same path

A rejected promise becomes gen.throw(ex) — thrown at the yield, inside evalGen, inside whatever Lisp try form was active. A network failure in an MCP call arrives as a catchable Lisp condition with a stack trace, not as an unhandled rejection somewhere outside the language. That falls out of the design rather than being built.

packages/interpreter/src/lisp.ts:550 — the two entry points 
export function runSync(interp, text)  { return driveSync(runGen(interp, text)); }
export function runAsync(interp, text) { return driveAsync(runGen(interp, text)); }
07

Three kinds of builtin, one flag

A builtin declares how it relates to waiting, and the call site branches on it. This is the part that repays close reading, because two of the three look identical from JavaScript.

packages/interpreter/src/lisp.ts — the entire dispatch 
if (fn instanceof BuiltInFunc) {
  if (fn.kind === "generator") return yield* fn.callGen(frame);
  const value = fn.call(frame);
  if (value instanceof Promise)
    return fn.kind === "plain"
      ? yield* fn.settle(value)      // SUSPEND — the program never sees a promise
      : this.async.watch(value);     // RETURN  — the promise IS the value
  return value;
}

Note the asymmetry. The plain branch is yield*, so the form's value is whatever the promise resolved to. The promise branch is a plain return — no yield at all — so the form's value is the promise, registered with the tracker and handed to the Lisp program as a first-class object it can hold, inspect and cancel.

The promises extension demonstrates both in one file, which is the clearest illustration in the codebase:

  ([list]) => Promise.all(toPromises(list)).then(arrayToList));

so the language gets both

(memory/recall "cfg") waits and gives you a memory — you never learn it was remote. (promise-all ps) gives you a handle you can pass around, race, or cancel, and (await p) is the one form that converts a handle back into a value. Implicit waiting and explicit concurrency are the same machinery under one flag.

08

What holds the promises the program keeps

Once a promise can be a Lisp value, something has to know about it. AsyncWork is a WeakMap of state plus a live set, and it is what makes cancellation possible at all.

packages/interpreter/src/async.ts 
start<T>(run: (signal: AbortSignal) => Promise<T>): Promise<T> {
  const controller = new AbortController();
  return this.record(run(controller.signal), controller);  // keeps the abort handle
}
cancel(promise) {
  this.live.delete(promise);
  const controller = this.tracked.get(promise)?.controller;
  if (!controller) return false;    // nothing to abort — see the docstring below
  controller.abort();
  return true;
}

The honesty in the language-facing docstring is worth quoting, because it admits the limit rather than papering over it:

packages/promises/src/promises.ts — (cancel promise) 
"Abort the work a promise came from and stop tracking it; returns t if there was
 something to abort. A promise is not cancellable in itself, so this aborts the
 request behind it — one built by promise-all and friends has nothing of its
 own to abort and returns nil."

A promise built by start carries an AbortController and really stops. A promise built by Promise.all owns no request, so cancel returns nil and says so. The model reading that prompt learns the actual rule instead of discovering it by surprise.

abortAll() is what a REPL reset calls: every live request is aborted, so a cancelled turn does not leave work running against a session that no longer exists.

09

The claims, as tests

This repo writes no design docs on principle: a constraint worth keeping is a name, a type, or a test that fails when it breaks. So the argument above is checkable.

packages/promises/test/async.test.ts:52 — suspension is position-independent 
it("resolves in an argument position", …      // (+ 1 (slow 2))          → 3
it("resolves inside a closure body", …        // (defun twice …) (twice 21) → 42
it("resolves inside a loop that runs many times", …
it("keeps tail calls from growing the stack while suspending", async () => {
  expect(await evAsync(
    "(defun down (n) (if (= n 0) 'done (down (- (slow n) 1)))) (down 200)"
  )).toBe("done");
});

That last one is the test I would point at first. Two hundred tail calls, each suspending in the middle, and the stack does not grow — because evalGen is a for(;;) trampoline that reassigns x rather than recursing, and generators preserve that across a suspension. Tail calls and waiting are usually a trade; here they compose.

packages/promises/test/async.test.ts:81 — nothing blocks 
it("lets the event loop turn during one eval", async () => {
  let ticked = false;
  setTimeout(() => { ticked = true; }, 0);
  await evAsync("(slow 1)");
  expect(ticked).toBe(true);        // the loop ran while the form was mid-evaluation
});
packages/promises/test/async.test.ts:87, :116 — both halves of the error story 
it("is catchable with try", async () =>
  expect(await evAsync('(try (boom) (catch (e) "caught"))')).toBe('"caught"'));

it("raises rather than half-running the program", () =>
  expect(() => runSync(interpWithSlow(), "(+ 1 (slow 2))")).toThrow(/cannot suspend/));

it("still runs everything that does not suspend", () =>
  expect(str(runSync(interp, "(+ 1 2)"))).toBe("3"));

"Raises rather than half-running the program" is the whole synchronous contract in one test name. A sync host does not get partial evaluation and a mystery; it gets a clean, catchable failure at the point that wanted to wait — and everything that did not need to wait still runs.

10

What it costs

Three real prices, none of them hidden.

  • Every frame is a generator frame. A tree-walker already allocates heavily; making evalGen and every helper a generator adds a constant factor to all evaluation, including the overwhelming majority of forms that never suspend. No benchmark in the repo pins that number, which is the gap worth closing — a measured figure belongs in a test that asserts it.
  • yield* is not optional. A helper called with a plain () instead of yield* silently loses the ability to suspend, and the failure shows up far away as a "cannot suspend" or a generator that never advances. The compiler does help here — the return type is Eval<T>, not T — but the discipline is still a discipline.
  • Two drivers mean two behaviours to keep true. Any form that suspends works in the agent and fails under runSync, by design. That divergence is pinned by tests rather than left to drift, which is the cost being paid properly.
the summary, in one line

Generators let this interpreter defer the question "am I allowed to wait?" from the place that wants to wait all the way up to the place that knows the answer. Forty-four lines, one flag on a builtin, and a language that can call the network mid-expression without becoming an asynchronous language.
