refactor/journal · views

What the chat and the trace show, before and after the journal

The refactor changes where every fact is stored. Before, it was merged onto a message. Now it is its own row. Each view folds those rows back onto the messages it draws. Most of the chat looks the same, while the trace views now show entries where they happened. This page puts each surface side by side.

1 · Chat body

One turn, as stored

A single turn in which a memory fires, the agent shows a todo, calls a tool and asks for approval. Before, the facts rode on the messages the step produced. After, each one is a row of type entry, in the order it happened. Entries recorded during a step carry about, the id of that step.

before messages table
0human"tidy my notes" · attachments: [notes.md]
1ai(plan …) · meta.memories: [deploy-cmd]
2toolintent · activity · asks{open} · ui
3ai"waiting on you"

Later, answering the ask deep-merged asks.answered into row 2 by patching it (messages.annotate).

after messages table
0human"tidy my notes" · attachments: [notes.md]
1entrymemory · about s1
2aiid s1 · (plan …)
3entryintent · about s1
4entryactivity started · about s1
5entryactivity done · about s1
6entryasks{open} · about s1
7toolid t1 · result
8ai"waiting on you"
9entryasks{answered} · about t1

Answering appends row 9 (messages.record). Nothing already stored is patched.

How the chat reads it back

before apps/app/src/lib/chat.tsx
export function toolIntent(message) {
  return readAnnotation(
    message.additional_kwargs, intentKey);
}
export function toolActivity(message) {
  return readAnnotation(
    message.additional_kwargs, activityKey) ?? [];
}
// memories: meta[m.id]?.memories on the ai row
after chat.tsx · lib/entries.ts
// once per render: entry rows → message.entries
foldEntries(turns, chatPlacement)

export function toolIntent(message) {
  return view(entriesOfMessage(message), intentKind);
}
export function toolActivity(message) {
  return view(entriesOfMessage(message), activityKind);
}

foldEntries attaches each entry to the message it belongs to. An entry with about goes to that step's tool row, and one with holding to the sub-agent's held row. Otherwise it goes by position, or onto a quiet placeholder row. The chat drops the memory kind.

2 · Trace view in the app

Memories move to where they fired

The app's trace panel folds with tracePlacement. It keeps memory entries standing, so each memory is a line of its own in the order it happened. Every other kind is carried onto its message, as in the chat. Before, memories hung under the ai message whose step had collected them.

before trace-view.tsx · TraceLine
usertidy my notes
ai(plan "Tidying notes" …)
◆ deploy-cmd · task deploy
tool⇢ read notes.md · done
aiwaiting on you
{shown.memory && stats?.memories && (
  <MessageMemories memories={stats.memories} />
)}
after trace-view.tsx · EntryLine
usertidy my notes
entry◆ deploy-cmd · task deploy
ai(plan "Tidying notes" …)
tool⇢ read notes.md · done
aiwaiting on you
{isEntryMessage(message)
  ? <EntryLine message={message} />
  : isToolMessage(message) ? <ToolMessage … />
  : <ChatLine … />}

The memory line now comes before the model's reply, because the memory fired before the model answered.

3 · Eval trace viewer

Entry lines join the report transcript

The eval report's transcript used to hold three roles, with an optional annotations bag on any line. Now entry is a fourth role, and the runner writes an entry line at the moment it sees the event. apps/trace-viewer draws it as a row with a yellow kind label.

before packages/evals/src/report.ts
const transcriptLineSchema = z.object({
  role: z.enum(["user", "assistant", "tool"]),
  content: z.string(),
  annotations: z.record(z.string(), z.unknown()).optional(),
});
after
const entryLineSchema = z.object({
  role: z.literal("entry"),
  kind: z.string(),
  value: z.unknown(),
  content: z.string(),
});
export const transcriptLineSchema = z.discriminatedUnion(
  "role", [messageLineSchema, entryLineSchema]);
before trace-viewer · transcript.tsx

tool"task deploy"
◆ deploy-cmd · task deploy
assistantRun task deploy.

Rendered from firedMemories(line.annotations?.memories) under the line that carried them. Other annotations were not shown.

after

memory◆ deploy-cmd · task deploy

Every kind gets a row. A memory renders as a chip, and anything else as its JSON value. Entries come before the tool line of their step.

before packages/components/src/memories.ts
// untyped parser, lenient
export function firedMemories(value: unknown) {
  // keeps items with a non-empty key,
  // body missing → "", bad `on` → dropped field
}
after @repo/journal-catalog/memory
const firedMemory = z.object({
  key: z.string().min(1),
  body: z.string(),
  on: z.string().optional(),
});
export const memoryKind = entryKind({
  name: "memory", schema: firedMemory, fold: every });

Stricter. A memory without a body, or with a non-string on, is now refused when recorded and skipped when read. An old report with annotations still parses, but its memories no longer show.

Found while writing this page

Two regressions from the step-id placement, fixed in 3b9505b4. First, while a step was still running, its entries were attached to its ai row, which the timeline doesn't read, so the live todo and progress disappeared until the result landed. Second, trace memories that named their step were attached to a message instead of standing on their own line, so they disappeared. A step now claims its entries only once its tool row exists, and standing placement wins over about. Two tests in apps/app/test/entries.test.ts cover both cases.

This comparison comes from reading the code and the diff against main. It was not checked against a running app.
