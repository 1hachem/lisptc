refactor/journal · review

Annotations out, journal in

The branch removes the per-step annotation bag and replaces it with an append-only journal. An extension now records one typed entry when something happens. Every layer above carries entries without knowing who made them, and each view reduces the kinds it shows.

1 · Before

How annotations worked

Each extension emitted onto a private topic, then hooked the annotate chain. At the end of a step the REPL ran that chain over the step's buffer. Every extension folded its own topic into a StepAnnotations value with two lanes, step and output.

The agent loop then merged those lanes into message metadata: the step lane onto the AI message's meta, the output lane onto the tool result's kwargs. The "collected", "concluded" and "live" events in packages/ai/src/turn.ts carried them. A throttled liveWatch re-ran the whole chain every 150 ms during a step to show progress.

2 · After

How the journal works

There is now one topic, journal, and one call, record(channels, kind, value). The REPL collects the topic from the buffer as a flat Entry[]. The agent loop yields one "entry" event per entry. The wire and Convex store each entry as its own message row with type: "entry". Readers reduce the run with a fold that the catalog ships beside each kind.

The primitive

new packages/shared/src/journal.ts
export interface Entry {
  readonly kind: string;
  readonly value: unknown;
}

export interface EntryKind<T> {
  readonly name: string;
  readonly schema: z.ZodType<T>;
}

export function readEntry<T>(entry: Entry, kind: EntryKind<T>) {
  return entry.kind === kind.name
    ? kind.schema.safeParse(entry.value).data
    : undefined;
}

export function latest<T>(entries, kind) {
  return entriesOf(entries, kind).at(-1);
}
new packages/interpreter/src/journal.ts
export const journal = topic<Entry>("journal");

export function record<T>(
  channels: Channels | undefined,
  kind: EntryKind<T>,
  value: T,
): void {
  journal.emit(channels, {
    harness: { kind: kind.name, value },
  });
}

The interpreter keeps 12 lines: the topic and the writer. Schemas left for the catalog.

Storage

Convex gains a fifth message type, "entry". The annotate mutation, which patched kwargs onto an existing row, becomes record, which appends rows. An optional about ties an entry to the message it concerns.

export const record = mutation({
  args: { chatId: v.id("chats"), about: v.optional(v.string()), entries: v.array(entry) },
  handler: async (ctx, { chatId, about, entries }) => {
    const ids = await appendTo(ctx, chat, entries.map(({ kind, value }) => ({
      type: ENTRY_TYPE, content: "",
      kwargs: about === undefined ? { kind, value } : { kind, value, about },
    })));
    await settleWaiting(ctx, chat);
    return ids;
  },
});

4 · Critique

What holds, and what I would change

The direction is right. The rule the repo states, "a fact is recorded as its own entry when it happens, never folded onto a step," is now how the code works. The findings below are ordered by risk.

Good

The seam got simpler

The annotate chain is gone, with StepAnnotations, its two lanes, mergeInto, conclude, the provisional live message and the 150 ms re-fold. Seven extensions lost a hook each. The interpreter no longer ships schemas for intent, asks, memory and activity, which were extension surfaces it had no business owning. packages/ai now handles one event type, "entry", instead of three.

High

Entries carry no step or turn identity, so the view guesses

packages/shared/src/journal.ts · apps/app/src/lib/entries.ts Folding.settle

An Entry is { kind, value } and nothing else. Annotations were attached to a step by construction. Entries are not, so the frontend rebuilds that link from row order. foldEntries carries an entry to the next tool message, else the previous tool message, else the next AI message, else a synthesized quiet tool row. Only about and holding are explicit. A steer, a sub-agent or a reordering in appendTo changes where an entry lands, and no test pins every branch of that ladder.

Direction: stamp step (already on channels.step) and a turn id on the envelope at record time, and have foldEntries place by id. Keep position as the fallback for rows written before the change.

High

waitsOnUser shares a 64-row window with entry rows

packages/backend/convex/lib/waiting.ts:8 TURN_SCAN = 64

Before, one tool row carried a step's whole bag. Now every activity started and done, every intent snapshot and every fired memory is its own row. A turn that asks for approval early and then runs a few MCP calls and intent updates can push the ask out of the 64 newest rows. latestTurn stops at a human or system row, but if it never reaches one within 64 rows it sees a truncated turn. The chat then leaves "waiting" while an approval is still open.

Direction: query back to the turn's human row by index instead of a fixed count, or keep a denormalized "open asks" field on the chat that record updates.

Medium

Old chats lose their intent, activity and asks

packages/backend/convex/migrations.ts is untouched on this branch

Rows written before the change hold their annotations in kwargs and meta. Every reader now looks only for type: "entry" rows. A chat opened after deploy shows no todo, no activity strip and no answered-ask labels for earlier turns. A chat that was "waiting" on an old-style ask is cleared by the next settleWaiting.

Direction: a one-shot migration that splits the old meta and output keys into entry rows with about set to the source row. If losing history is acceptable, say so in the PR's blast radius.

Medium

One full SSE snapshot per entry, with no throttle

packages/ai/src/stream.ts case "entry"

case "entry":
  this.stepEntries.push(event.entry);
  this.wire.push(entryMessage(event.entry));
  return this.snapshot();   // writes lighten(this.wire) in full

The old live path was throttled to 150 ms and diffed. Now each entry rewrites the whole lightened wire. Intent records its complete state on every show, so a loop that ticks progress 200 times sends 200 snapshots and stores 200 rows, of which latest keeps one. The cost grows with turn length times entry count.

Direction: coalesce entries inside one event-loop tick before snapshot(), and let a latest-wins kind replace its previous unflushed row instead of appending.

Medium

The fold is a convention beside the kind, not part of it

packages/journal-catalog/src/*.ts

Each kind has a different reduction: merge by id, concat-and-merge, latest, or plain list. That knowledge lives in free functions a reader has to know to call. A view that calls entriesOf(entries, activityKind) instead of activityOf shows every activity twice, started and done. Nothing in the types stops it. activityOf is also quadratic through findIndex, and views re-run it on every render.

Direction: put the reducer on the kind, entryKind({ name, schema, fold }), and expose one view(entries, kind). Use a Map for the merge-by-id fold.

Low

Validation happens only on read

record<T> trusts the compile-time T. A value that fails the schema (a progress with done > total, a min(1) key) is stored and streamed, then readEntry's safeParse drops it with no trace. Parsing in record would fail at the extension that wrote it, which is the boundary rule @repo/env already follows.

Low

Two names for one shape, and an unchecked cast

shared/src/journal.ts Entry · shared/src/messages.ts JournalEntry · repl/src/repl.ts payload as Entry

JournalEntry is the zod twin of Entry. One schema in journal.ts with its inferred type would serve both. liveEntries casts the payload without the check that entryOf performs on the wire side.

Low

Naming collides with the new vocabulary

ActivityEntry has a field named kind ("llm", "mcp") and sits inside an Entry whose kind is "activity". The ui kind is exported as viewKind. memories became memory. Renaming the inner field to source and matching export names to kind names would make grep reliable.

Low

Inbound is still a bag

Received is Record<string, unknown> read with readReceived(received, kind). What comes in with the human message is keyed by kind name but is not a list of entries. That asymmetry is fine today. It will bite the first time two values of one kind arrive together.

Low

Live dedupe depends on reference identity

packages/ai/src/turn.ts whileRunning

seen is a Set<Entry>. It works because bufferTransport.collect returns the same payload objects the live transport saw. A transport that clones, or a buffer that round-trips through JSON, would double every live entry. An id on the entry would remove that coupling and help the first finding too.

Verdict

Merge after two fixes

The refactor removes more mechanism than it adds, and the boundary between interpreter, extensions and views is cleaner for it. Before merging I would fix the waitsOnUser window and decide on old rows: migrate them or state the loss. The missing step identity is the deeper problem and could follow in its own change, since adding an id to Entry also fixes the live dedupe and makes foldEntries deterministic.

  1. Scan waitsOnUser to the turn's human row, not 64 rows.
  2. Migrate or explicitly drop annotation-shaped rows.
  3. Add step, turn and entry ids to Entry; place by id.
  4. Coalesce snapshots; collapse latest-wins kinds.
  5. Move each fold onto its kind and validate in record.
