The Channel Patchbay

The interpreter never writes to a screen. It addresses an utterance to an audience and hands it to a bus. Who is listening — a terminal, a step buffer, an eval recorder, a socket that did not exist last week — is somebody else’s decision.

4 emitters 3 topics 2 audiences ~100 lines of bus
01 · The one idea

An emission is a payload addressed per audience

Two audiences read this REPL. A person watches a transcript scroll past. A model reads a step report and decides what to evaluate next. They want different things from the same act of speaking: the person wants the whole 1,200-word table, the model wants 250 words and a note saying what it is missing.

Until this refactor that asymmetry was spelled three ways. The core interpreter had a private say (user only) and a private tell (both), the compactor had its own say taking a {model, user} pair, and the memory bank had a third say that was not really an emission at all. Four call sites, three vocabularies, one act.

Before — three verbs 
// lisp.ts
private say(text)  { output.emit(ch, ["user"], text) }
private tell(text) { output.emit(ch, ["user","model"], text) }

// compaction.ts
say(bounded) {
  if (bounded.user  !== "") output.emit(ch, ["user"],  bounded.user)
  if (bounded.model !== "") output.emit(ch, ["model"], bounded.model)
}

// memory.ts
private say(key, body) { ...budget; fired.emit(ch, ["user"], …) }
After — one verb 
type Addressed<T> = Partial<Record<Audience, T>>

output.emit(ch, { user: text })                  // echo
output.emit(ch, { user: text, model: text })     // doc
output.emit(ch, { user: full, model: clipped })  // compacted echo
fired.emit(ch,  { user: { key, body } })         // a memory fires

// and Bounded is now what it always was:
type Bounded = Required<Addressed<string>>

say was Addressed with the model dropped. tell was Addressed with both fields equal. The compactor’s Bounded was Addressed with both fields required. Once the payload carries its own addressing, the three verbs collapse into the one the bus already had: emit.

The grouping moved with it. emit now folds audiences that received an identical payload into a single envelope addressed to both — which is exactly what tell used to hand-write, and what the compactor used to get wrong by sending the same doc string twice.

02 · Anatomy

Four types, and only one of them is a class

The whole bus is about a hundred lines. It is worth reading in full before trusting any diagram of it.

interface Envelope<T = unknown> {
  topic: string
  to: readonly Audience[]     // "user" | "model"
  step?: number               // stamped by Channels if absent
  payload: T
}

interface Topic<T> {                        // a typed door onto the bus
  readonly name: string
  emit(ch: Channels | undefined, addressed: Addressed<T>): void
  on(ch: Channels, listener: (payload: T, e: Envelope<T>) => void): () => void
}

interface ChannelTransport {                // a sink that takes everything
  send(envelope: Envelope): boolean         // false => unsubscribe me
  close?(): void
}

class Channels {
  on(topic, listener): () => void           // one topic, typed via Topic.on
  onAny(listener): () => void               // every envelope
  pipe(transport): () => void               // every envelope, sink-shaped
  emit(envelope): void                      // fan out, synchronously
  step = 0
}

Topic vs transport is the whole split

A topic is typed and narrow: output carries strings, note carries {kind, text}, memory carries {key, body}. Code that cares about one kind of event subscribes through the topic and gets its payload type back.

A transport is untyped and wide: it receives every envelope on the bus and decides for itself what to do. That is the port a terminal, a socket, or a log file plugs into. It returns false to unsubscribe itself, which is how a dead client cleans up without anyone tracking it.

Emitting through Topic.emit also accepts undefined channels and no-ops — extensions hold channels?: Channels until they are attached, and that used to mean a guard at every call site.

05 · Who listens

The same step, four destinations

The CLI is the simple case: a transport that writes the user’s half of output to stdout as it arrives, live, mid-step. The web UI is the interesting one, because it is not a transport. It sits downstream of the step buffer.

The unfinished half. Streaming the web UI mid-step is not a redesign. The envelopes already exist, already carry to and step, and already flow while the step runs. What is missing is a transport on the API process that forwards to.includes("user") envelopes down the SSE connection the browser is already holding.

That is the return on the decoupling: the capability was built the day the bus was, and nobody had to know about it.

06 · Extension point

Connecting another service is twelve lines

A transport needs one method. It gets every envelope, filters for what it cares about, and returns false when it is finished — at which point the bus drops it without anyone calling a teardown.

import type { ChannelTransport } from "@repo/interpreter/channels"
import { output } from "@repo/interpreter/topics"

function wsTransport(socket: WebSocket): ChannelTransport {
  return {
    send(e) {
      if (socket.readyState !== socket.OPEN) return false   // drop me
      if (e.topic !== output.name) return true              // not mine
      if (!e.to.includes("user")) return true               // not my audience
      socket.send(JSON.stringify({ step: e.step, text: e.payload }))
      return true
    },
    close() { socket.close() },
  }
}

const detach = interp.channels.pipe(wsTransport(socket))

No emitter changes. No extension changes. No type in the interpreter changes. The same shape covers an OpenTelemetry exporter (map topic to an event name, step to a span attribute), a JSONL run recorder, a Slack relay, or a second terminal watching a shared session.

The one thing a transport must not do is throw. A throwing transport is removed from the set silently, and it will not be told.

07 · Trade-offs

What this costs, stated plainly

Synchronous fan-out

emit returns only after every listener and transport has run. Ordering is total and trivially debuggable, allocation is near zero, and a stack trace crosses the bus intact.

Cost A slow transport slows the interpreter. There is no backpressure and no queue: a socket write that blocks blocks evaluation.

Failures degrade to a note

A listener that throws is caught, and the bus emits a note to the model saying which topic broke. A REPL that must keep running does not die because a renderer had a bad day.

Cost A throwing transport is deleted from the set with no report at all. A CLI whose stdout sink died goes quiet and never learns why.

No history, no replay

Channels keeps nothing. Anything that wants a transcript pipes a buffer for as long as it needs one, which is exactly what the REPL does per step.

Cost A transport attached mid-step sees only the rest of the step. There is no offset, no resume, no audit log without adding a sink that keeps one.

Two audiences, closed set

Audience is derived from the AUDIENCES tuple, so the type and the iteration order cannot drift. Adding one is a one-line change with a compiler-checked blast radius.

Cost Audience is a global enum, not a subscriber identity. Two humans on a shared session are one "user"; per-recipient routing would need a different key.

Typed at the topic, untyped at the transport

Subscribers using Topic.on get their payload type. It is the right trade: the narrow consumers get safety, the wide one stays open.

Cost Envelope<unknown> means every transport casts. A transport that switches on topic and casts wrong compiles fine and fails at runtime.

Two paths reach the model

The bus carries what is said during the step. The step report is assembled after it: truncation notes, the recall buffer, the error record.

Cost The real tension in the design. “What did the model see?” cannot be answered from envelopes alone, which makes the bus an incomplete audit surface.
08 · Alternatives

What the industry does instead

None of this is novel machinery. It is a publish-subscribe bus with one unusual dimension — routing by recipient rather than by severity or type — and it is worth being precise about which established pattern it is a small version of.

ApproachWhat it would giveWhat it would cost here
Node EventEmitter Zero code. The same synchronous fan-out, already in the runtime. Untyped payloads, no envelope metadata, no to, and listener errors that crash the process by default. The custom bus exists mostly to add those four things.
RxJS / observables Composition: filter, buffer, debounce, backpressure operators, and a per-step window as a first-class object. A dependency in the interpreter, which the layering forbids on purpose. Real operator power for a bus with three topics and four sinks.
Redux-style middleware One action, many observers, with interception: a middleware could rewrite an envelope before it lands. Middleware couples the chain in order. The compactor already is the interception layer, expressed as a different payload rather than a wrapper.
OpenTelemetry signals + exporters The closest mature analogue: topic = signal, transport = exporter, plus batching, retry, sampling and a wire format. Heavy for in-process rendering. Worth adopting the moment envelopes leave the process — batching and retry are the two things a hand-written socket transport will get wrong.
CloudEvents envelope A standardised envelope (id, source, type, time, data) that other services already parse. Nothing, really. Envelope is a private CloudEvent with to added and id/time missing. If envelopes ever cross a boundary, renaming toward it removes a translation layer.
Structured logging sinks (pino, bunyan) The daily-driver version of this pattern: one call, many sinks, filtered by level. Levels are a severity dimension. to is a recipient dimension, and no logger models it — which is the one genuinely unusual thing in this design.
Actor mailboxes (Erlang, Akka) Addressed, asynchronous messages with supervision and isolation — a real answer to the slow-transport problem. Point-to-point, not broadcast. Every sink would need an address and the emitter would need to know it, undoing the decoupling.
Durable log (Kafka, event sourcing) Replay, offsets, audit, multiple independent readers at different positions. Absurd for a single-process REPL — until runs need to be replayed or audited after the fact, which is the one scenario that would justify it.

The honest summary

For an in-process interpreter with a handful of sinks, a hand-rolled synchronous bus is the right size: a hundred lines, no dependency, total ordering, and a transport interface anyone can implement in a sitting. It buys the one property that matters — the interpreter does not know who is listening — at a price that is currently zero.

It starts costing when envelopes leave the process. At that point the missing pieces are all the same missing piece: asynchrony. Batching, retry, backpressure, replay. The fix is not to replace the bus but to write one transport that owns a queue, and to steal OpenTelemetry’s exporter semantics rather than inventing them.
